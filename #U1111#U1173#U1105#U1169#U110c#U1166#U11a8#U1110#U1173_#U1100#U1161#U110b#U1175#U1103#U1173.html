Section 01 · Mission

어떤 문제를 푸는가

Core IMS 망에는 제조사(벤더)가 다른 장비 관리 시스템(EMS)이 섞여 있습니다. 같은 "REGISTER 성공 건수"라도 A사는 RegSucc, B사는 VS.RegisterSuccess, C사는 reg_ok_cnt라고 부릅니다. 시각 표기도, 수집 주기도, 비율의 스케일(0~100 vs 0~1)도 제각각입니다. 지금은 새 장비가 들어올 때마다 사람이 벤더 문서를 읽고 변환 코드를 새로 짜는 것이 현실이고, 그게 병목입니다. 여러분이 만들 것은 두 가지입니다.

BUILD ①

파이프라인 — 결정론적 변환 엔진

매핑 규칙에 따라 3사의 원본 데이터(PM/CM/FM)를 하나의 표준 스키마로 변환합니다. 같은 입력에 같은 규칙이면 언제 돌려도 같은 출력이 나와야 합니다. 매일 밤 도는 운영 배치가 어제와 다른 답을 내면, 그건 자동화가 아니라 사고이기 때문입니다.

BUILD ②

에이전트 — 문서를 읽고 규칙을 만드는 LLM

벤더 인터페이스 문서(ICD)를 읽고 파이프라인이 쓸 매핑 규칙을 스스로 만들어냅니다. 벤더가 개정판 문서를 내놓으면 규칙도 따라서 갱신할 수 있어야 하고, 그 갱신이 기존에 잘 되던 변환을 깨뜨리면 안 됩니다.

어떻게 만들지는 전적으로 여러분의 몫입니다. 매핑 규칙을 어떤 형식으로 표현할지(YAML? JSON? 생성된 파이썬 코드?), 에이전트를 어떻게 설계할지, 어떤 AI 코딩 도구를 쓸지 — 전부 자유이고, AI 도구 사용은 금지는커녕 적극 권장합니다. 단, AI가 만든 결과가 맞는지 검증하는 책임은 팀에 있습니다. 이 프로젝트의 성패는 "돌아간다"와 "맞는다"의 차이에서 갈립니다.

Section 02 · Architecture

전체 그림 — 무엇이 제공되고, 무엇을 만드는가

위쪽은 항상 도는 데이터 경로(원본 → 어댑터 → 변환 엔진 → 통합 JSONL → 자가검증), 아래쪽은 문서가 갱신될 때만 도는 규칙 경로(ICD 문서 → 에이전트 → 규칙 저장소)입니다. 두 경로는 rules/ 규칙 저장소에서만 만납니다. YOU BUILD 표시가 여러분이 만드는 것, 나머지는 킷에 들어 있습니다.

어댑터는 왜 제공하나

adapters는 원본 파일 → {원본필드명: 값} 평면 딕셔너리까지만 합니다.

from adapters import parse_file

for raw, err in parse_file("data/public/raw/B_IMS-CSCF-B01_PM_20260601.xml"):
    print(raw)   # {'localDn': 'IMS-CSCF-B01', 'endTime': '2026-05-31T15:15:00Z',
                 #  'VS.RegisterAttempt': '5182', 'VS.CpuUtilRatio': '0.3391', ...}

여기까지는 XML 네임스페이스와의 씨름일 뿐 배울 게 없어서 미리 해뒀습니다. 진짜 문제는 그 다음입니다 — VS.CpuUtilRatio가 표준 스키마의 어떤 필드이고, 0.3391에 100을 곱해야 한다는 사실을 문서에서 읽어내는 일. 어댑터는 그걸 전혀 모릅니다.

충돌 시 우선순위 — 사전이 이깁니다. 벤더 문서와 counter_dictionary.md가 다르게 말하면 사전이 정답입니다. 단위 정책(비율 = percent 0~100 · 시간 = ms · 시각 = KST ISO 8601)에 예외는 없습니다.

Section 04 · Contract

지켜야 할 것은 단 두 가지 — 나머지는 전부 자유

① CLI 규약 — 채점기가 이 명령을 그대로 실행합니다

제출물 최상위에 pipeline.py, agent.py, rules/, adapters/가 있어야 하고, 아래 세 명령이 정확히 이 인자 이름으로 동작해야 합니다. 인자 이름이 하나라도 다르면 채점기가 실행 자체를 못 합니다.

# ① 변환: 원본 + 규칙 → 통합 JSONL
$ python pipeline.py transform --input <raw_dir> --rules <rules_dir> \
                               --out <unified.jsonl> [--rejected <rejected.jsonl>]

# ② 규칙 제안: 벤더 문서를 읽고 매핑 규칙을 생성/갱신
$ python agent.py propose --doc <ICD.md> --vendor <VENDOR_X> \
                          --rules <rules_dir> --out <rules_dir> [--sample <raw_dir>]

# ③ 규칙 점검: 생성된 규칙이 실제 원본에 적용되는지 확인
$ python agent.py validate --rules <rules_dir> --input <raw_dir>

rules/ 안의 형식은 완전히 자유입니다. 채점기는 이 디렉터리를 열어보지 않는 블랙박스로 취급합니다. YAML이든 JSON이든, 에이전트가 생성한 파이썬 코드든 — 여러분의 파이프라인이 읽어서 변환할 수만 있으면 됩니다. 매핑 규칙을 어떤 형식으로 표현할지가 이 과제의 첫 번째 설계 결정이고, 멘토링에서 그 결정의 근거를 묻습니다.

② 운영 제약 — 변환은 이런 환경에서 실행됩니다

pipeline.py transform은 네트워크가 차단된 환경에서, 같은 입력으로 두 번 실행되어 결과가 diff로 비교됩니다. 1회 제한시간은 10분입니다.

두 실행의 결과가 1바이트라도 다르면 결정론 위반입니다. 이 조건에서 살아남는 아키텍처를 설계하는 것부터가 과제의 일부입니다 — LLM을 어디에 쓸 수 있고 어디에 쓸 수 없는지, 이 제약이 알려줍니다. bash submit_check.sh로 언제든 같은 검사를 미리 돌려볼 수 있으니 첫 주에 한 번 돌려보길 강력히 권합니다.

Section 05 · Data Reality

데이터의 함정 — 미리 알려드립니다

원본에는 실제 운용망에서 늘 나오는 오염이 약 5% 섞여 있습니다. 함정이 아니라 현실입니다. 오염을 어떻게 다루는지도 실력의 일부로 봅니다.

유형기대하는 처리
감점 대상 중복 레코드제거해야 정답 (안 하면 감점)
주의 파일 내 시간 역전정렬해서 처리
가점 기회 결측 필드 · 카운터 0 리셋 · 잘못된 severity 코드 · 깨진 CSV 행 복구 불가 → 버리고 --rejected에 사유 기록 (누락 자체는 감점 없음, 사유를 남기면 가점)
Section 06 · Self-Validation

자체 검증 — 여러분이 보는 점수가 실제 점수입니다

왜 검증인가. AI가 만든 변환 결과는 거의 항상 "그럴듯해 보입니다". CPU 사용률 0.34%도, 세션 설정 시간 0.14ms도 스키마상으로는 멀쩡한 값입니다 — 단위 변환을 빼먹었다는 것은 비교해봐야만 드러납니다. 그래서 이 킷의 eval/validate.py는 멘토의 채점기와 완전히 동일한 비교 엔진(compare_core.py)을 씁니다. 숨겨진 채점 기준은 없습니다. 여러분이 공개 데이터에서 보는 점수가, 멘토가 히든 데이터에서 재는 점수와 같은 방식으로 계산됩니다. 검증 없이 만든 것은 완성이 아니라 추측입니다.

# 1) 원본을 눈으로 먼저 보세요 (3사 포맷이 전부 다릅니다)
$ python -c "from adapters import parse_file; \
             print(next(parse_file('data/public/raw/A_IMS-CSCF-A01_PM_20260601_0000.csv'))[0])"

# 2) 규칙을 만들어 변환하고
$ python pipeline.py transform --input data/public/raw --rules rules \
                               --out unified.jsonl --rejected rejected.jsonl

# 3) 스스로 채점하세요 — 몇 번이든
$ python eval/validate.py --unified unified.jsonl --golden data/public/golden_sample/ \
                          --exclusions data/public/exclusions.json --rejected rejected.jsonl

# 4) 제출 형식·결정론·실행 시간 점검
$ bash submit_check.sh . data/public/raw

점수는 이렇게 계산됩니다

지표뜻가중치
schema_validity출력이 표준 스키마에 맞는가15
f1있어야 할 레코드를 다 냈는가 / 없어야 할 레코드를 지어내지 않았는가30
field_accuracy필드 값이 정답과 일치하는가 (단위·시각 변환 포함)55
노이즈 처리 가점최대 +5

환각 페널티 — 모른다고 말하는 쪽이 이깁니다. field_accuracy는 골든에 없는 필드를 지어내도 분모에 더해 감점합니다. 문서에 근거가 없으면 채우지 마세요. 모르는 필드는 규칙에 unmapped로 사유와 함께 남기는 것이 정답입니다.

Section 07 · Final Deliverable

최종 산출물

프로젝트 종료 시점에 제출하는 것은 아래 네 가지입니다.

산출물기준
필수 팀 저장소 (또는 zip) 최상위에 pipeline.py · agent.py · rules/ · adapters/. 외부 패키지를 썼다면 requirements.txt 포함. submit_check.sh 통과 상태여야 합니다.
필수 공개셋 성적표 3사 전체 validate.py 결과. 완주 기준: field_accuracy 99% 이상. v1.1 개정 적용 후에도 기존 v1.0 데이터 점수가 유지되는지 함께 제시.
필수 설계 결정 로그 규칙 표현 형식, 에이전트 설계, 노이즈 처리 정책 등 무엇을 골랐고, 무엇을 버렸으며, 왜인지를 담은 기록. 분량보다 솔직함이 중요합니다.
발표 15분 데모 에이전트가 문서를 읽고 규칙을 만들어 변환·검증까지 도달하는 과정을 라이브로 시연.

팀 운영 힌트. 6명이 전원 코딩할 필요는 없습니다 — 벤더 문서 분석과 매핑 표 작성, 검증·QA, 결정 로그 기록은 코드만큼 점수를 좌우하는 역할입니다. 막혔을 때는 개발 코치에게 먼저 물어보세요. 이틀 이상 같은 자리에 서 있는 것이 가장 나쁜 상태입니다. 에이전트용 LLM API 키는 코치를 통해 제공됩니다.

Section 08 · Mentoring

멘토링 — 멘토는 그 자리에서 무엇을 돌리는가

멘토링 미팅에서 멘토는 여러분의 코드를 그 시점의 스냅샷 그대로 받아, 비공개 채점기(grade.py)로 아래 세 가지를 실행하고 결과를 피드백으로 돌려줍니다. 채점기의 비교 규칙은 여러분이 가진 eval/compare_core.py와 1비트도 다르지 않습니다 — 다른 것은 데이터와 문서뿐입니다.

멘토가 돌리는 것투입물확인하는 것
E1 히든 데이터 변환 여러분이 본 적 없는 장비 4대의 원본 제출 규칙 그대로 변환 실행 — 공개 데이터에만 통하는 규칙인지, 특정 장비 이름에 하드코딩돼 있지는 않은지
E2 히든 문서 일반화 공개된 적 없는 개정판 문서(v1.2) agent.py가 처음 보는 문서만으로 규칙을 만들어 변환. 3회 실행 — 한 번 얻어걸리는 팀과 매번 되는 팀을 구별합니다
E3 회귀 방어 E2로 갱신된 규칙 + 기존 데이터 규칙 갱신이 기존에 잘 되던 변환을 깨뜨리지 않았는지

미팅에 가져올 것은 두 가지면 충분합니다: 그 자리에서 실행 가능한 코드 스냅샷과 설계 결정 로그. 멘토는 점수와 함께 "왜 그렇게 설계했는지"를 묻습니다 — 정답을 맞히는 자리가 아니라, 여러분의 접근을 검증해보는 자리입니다.

요약하면. 공개셋에서 validate.py 점수를 끌어올리고, 특정 장비·특정 파일에 기대지 않게 만들고, 에이전트가 처음 보는 개정 문서에도 매번 안정적으로 동작하게 만들면 됩니다. 멘토링에 깜짝 요소는 없습니다 — E2의 문서가 처음 보는 것이라는 점만 빼면, 전부 이 문서에 적힌 그대로입니다.
